# PayPal subscription lifecycle (Sandbox)

Recomvia uses PayPal's **revise subscription** API for Essential, Growth, and Pro changes. A change keeps the existing PayPal subscription ID. PayPal may return an approval URL; the old plan remains the application's entitlement until a subsequent PayPal GET or verified webhook confirms the new active plan. PayPal applies the new price at the next billing cycle and does not prorate it automatically. Starter remains a separate, report-scoped, one-time order.

The create route requires an authenticated organization member, checks for an existing recurring agreement, and returns `already_active` for the same plan or `plan_change_required` for a different plan. Suspended and payment-failed agreements also block a new checkout until billing review because they may resume billing. The UI sends active-plan changes to `revise-subscription`. A 15-minute organization claim prevents concurrent create or revise requests from opening multiple checkout flows. It expires after abandonment; inactive PayPal rows remain audit history and do not grant access or block a later checkout.

Migration `0007_round_veda.sql` adds the claim table and insert/update triggers preventing a **new** second active paid row for the same organization. Active writes in sync and webhook processing also use conditional SQL. A conflicting new PayPal activation is cancelled and verified server-side before its event is acknowledged; if PayPal does not confirm cancellation, the webhook fails for retry. Webhook event IDs remain recorded in `payment_events` for idempotency. Cancellation, suspension, expiry, and payment failure revoke entitlement without deleting subscription history.

Existing duplicate active agreements are deliberately not cancelled by a page visit or migration. The database can already contain multiple PayPal agreements, and a database migration cannot verify which ones PayPal still bills. Until reviewed, the UI blocks checkout and shows a billing conflict. Entitlement resolution selects one row by latest `updated_at`, then ID, and never combines features. To remediate an existing organization in Sandbox: inspect all of its active `provider_subscription_id` values in PayPal, keep the intended current agreement, cancel the others in PayPal, verify each cancellation with PayPal GET, then sync their stored statuses through the authenticated sync route or verified webhooks. Keep every historical row and payment event. Review the organization's resulting single active agreement before allowing another plan change.

This release does not call PayPal Sandbox or change existing staging agreements during local build and tests. The tests use a mocked PayPal transport.
